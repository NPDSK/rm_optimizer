# RM Optimizer — Acceptance Criteria

Статус: DESIGN DRAFT, 12 сентября 2026. Это целевые black-box проверки, **не отчёт о прохождении текущего приложения**.
Требования: [PRODUCT_REQUIREMENTS](PRODUCT_REQUIREMENTS.md). Открытые D-решения: [реестр](PRODUCT_VISION.md#product-decisions-requiring-owner-approval). Проверки, зависящие от D-ID, подтверждают рекомендуемый вариант после его утверждения.

## Тестовые участники и данные

Installation I1 и изолированная I2; пользователи Admin, Manager-A, Manager-B, Alice, Bob, Viewer и JiraProjectAdmin без RM grant. Planning Team A имеет external ID `team-a`, B — `team-b`; display name можно изменять/дублировать. Context CA связан с A, CB с B; Jira projects P1/P2 и board Z — отдельные источники. Alice вручную включена в A, в B membership отсутствует. В A и B есть независимые policy/profile/scope/input revisions и опубликованные baseline.

Work fixtures содержат stable issue IDs; unassigned issue с Team A; issue, назначенный Alice, с Team B; Epic как executable и другой Epic как container; siblings, Blocks, внешний prerequisite, DONE/IN_PROGRESS, missing estimate/value, optional и mandatory deadline conflicts. Источник умеет возвращать pagination, partial failure, revoked permission и reordered results. Worker умеет возвращать duplicate, delayed, failed и invalid output. Это тестовые модели, не имена реальных customer records.

Для каждой проверки наблюдается UI/API-результат и сохранённое состояние после reload/retry. Одного совпадения текста кнопки недостаточно. Технические logs дополнительно проверяются на отсутствие fixture customer content/account IDs.

## Сквозной release journey

**AC-051 — AUTH-001, CTX-001, TEAM-004, PROF-002, CAP-002, SCOPE-001, MAP-001, READY-001, OPT-001, SCEN-001, PUB-001, LOOP-003.**

Given новая installation и approved D-решения. When authority назначает Manager, он создаёт CA, явно выбирает Team A, approves Alice join/profile/availability, подключает P1/P2, подтверждает scope/mappings/horizon/policies, исправляет readiness, получает Python result, review/publish; Alice затем сообщает change, Manager refreshes/reviews/replans/publishes. Then ни на одном переходе нет auto role elevation, hidden membership/scope inference или hidden publish; Alice видит собственный новый план, бизнес — разрешённый baseline, каждая версия имеет immutable lineage. Повторный вход восстанавливает Context, очередь запросов и текущий published plan. Это критерий целостности предлагаемого MVP D-01.

## Как проверять

- Node application/domain: состояния, ACL, Context propagation, input semantics и operation retries.
- Persistence integration с реалистичной моделью SQL unique/revision guards: конкурентные создания, bind/migration, cross-context isolation, interrupted writes. In-memory adapter отдельно проверяет тот же repository contract и не заменяет SQL проверки.
- React tests: route/Context race, role/read-only/loading/pending/empty/error states, readiness, preview/publish, inbox; frontend build при реализации UI.
- Python tests/fixtures: hard constraints, objective order, contracts, truthful termination, overflow, gates/value; service integration отдельно от математического solve.
- Реальный Jira smoke: разные пользователи и source permissions, cross-project Team-field/board, pagination, unavailable identity sync, end-to-end publish/replan. Не считать локальный mock доказательством установленной Forge работоспособности.
