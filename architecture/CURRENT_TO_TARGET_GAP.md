## Что уже изменилось относительно раннего аудита

Репозиторий **уже содержит первую multi-Planning-Team реализацию**. Нельзя описывать его как UI, который всегда вызывает direct Jira request первых project issues:

- `getPlanningTeamContext` разрешает normalized external Team ID через installation-wide lookup и safe legacy binding;
- migration v039 добавляет unique external identity Team;
- `App` и `TeamSetup` используют общий `activeTeamExternalId`;
- `getTeamScopedIssues` читает сохранённый TeamWorkScope, scoped display не требует готового canonical mapping;
- frontend отбрасывает запоздавшую загрузку A после выбора B;
- для externally bound Team попытка заменить membership source другим external ID получает `TEAM_CONTEXT_SWITCH_REQUIRED`.

Но `planningTeamContext` всё ещё возвращает **Team**, не first-class Planning Context с собственными sources/horizon/ACL/versions. Другие application paths продолжают использовать project default Team. Первая multi-Team реализация — полезная промежуточная база, а не завершённая целевая архитектура.

## SQL, indexes и минимальный structural gap

Источник фактического migration plan — [src/adapters/sqlMigrations.js](../../src/adapters/sqlMigrations.js), сейчас v001–v039. [persistence/design/001_application_core.sql](../../persistence/design/001_application_core.sql) — design reference, не доказательство deployed schema. Foreign keys/cascading multi-table transactions в текущем плане не задаются; orchestration рассчитана на повторяемые отдельные операции.

| Группа миграций | Текущие tables/ключи | Что нужно для target |
|---|---|---|
| v001–v004 | `projects` unique platform/external_project_id, `current_published_roadmap_id`; `teams.project_id NOT NULL`, `current_mapping_profile_id`; mapping version unique Team+Project+version | Context owner/published pointer; source mapping-set activations. `project_id` у Team на время compatibility — origin provenance, не ACL/identity |
| v005–v010 | resources Team+platform+externalresource; work_items Project+platform+externalwork, dependencies/overrides/execution events project/team; diagnostics | Shared UserIdentity + Team profiles; SourceWorkIdentity + Context projection/history bindings; diagnostics access/retention |
| v011–v017 | Project roles/skills, resource-role/skill links, Team availability, project/team constraints/change requests | Catalog decision D-08, Context-owned constraints/requests, separate membership joins и ACL, approved revision links |
| v018–v023 | Roadmap versions unique Project+Team+version, version items/allocations, project/team execution snapshots и runs | Context-scoped version/run/snapshot identity, input manifests, attempts/publish operations и pointer fencing |
| v024–v032 | Team WIP/structure/gates; primary role/type/kind/hierarchy additions | Сохранить алгоритмы, Context policies/gates/structure owners и immutable revisions |
| v033–v038 | One source/workscope/capacity policy per Team; platform memberships unique Team+platform+externalTeam+resource; overrides Team+resource+provenance; resource settings Team+resource | Membership tables переиспользовать; source generation/finalization; Context WorkScope version/source set и allocations отдельно от Team membership/capacity |
| v039 | Unique `uq_teams_platform_external(platform_type, external_team_id)` | Уже поддерживает несколько внешних Teams в installation. Не решает first-class Context, grants, cross-context work overlays или publish ownership |

**Можно ли обойтись без migration?** Для уже реализованного разделения A/B на Planning Teams — текущий v039 и Team-specific children в основном достаточны. Для целевого продукта с самостоятельным Context — нет: отсутствует owner ID и связи в persistence, а unique work key и project pointer не выражают нужную изоляцию.

Минимальное **поэтапное** расширение, не новый DDL в этом milestone:

1. Context identity/lifecycle/revision, ContextTeam, legacy binding, Context grants/installation authority и stable user identity refs; не переименовывать Team.id в Context.id.
2. Context sources/scope revisions/mapping activations/horizon/policies; link существующие Team defaults и source profiles по approved backfill.
3. Source identity + Context work projection/overlay relations, включая structure/deps/gates/constraints; сохранить IDs или explicit legacy alias для historical references. Контракт нового upsert не меняет чужого owner.
4. Context ownership для runs/versions/snapshots, approved input manifests/operation attempts, unique per-Context version и conditional published pointer. Shared commitment guard реализуется перед publish по D-03.
5. Временные legacy compatibility reads, verification/cutover, затем отдельное retirement. Не редактировать уже применённые v001–v039 и не полагаться на destructive rebuild.

Не все tables нужны в первом вертикальном milestone: schema расширяется вместе с работающим use case. SQL unique/revision primitives проверяются на поддерживаемом Forge SQL окружении, а не только mock query text.

## Переход данных и legacy Cools/Legal

Текущая application binding проверяет unbound source/scope/platform evidence. Это полезный guard, но не машина восстановления прежней organizational принадлежности manual data. Если один internal Team ранее менял A→B, происхождение ручного Alice/capacity/constraints могло не сохраняться.

Предлагаемый D-11 путь:

1. **Инвентаризация.** Read-only export/manifest legacy project/team/source/scope/resource/membership/profile/work/roadmap references и counts. Отдельно записать source generation/freshness, external IDs и duplicates. Live site проверять только в implementation milestone с разрешением; текущие Cools/Legal данные не экспортировались.
2. **Сохранение.** Зафиксировать immutable migration snapshot и binding plan. Не менять IDs людей/Team/roadmap и не назначать ownership по `CreDits planning team`, latest source name, assignee или порядку списка.
3. **Однозначные связи.** Existing bound Team A остаётся A; unbound единственная согласованная external identity может связаться с тем же Team ID. Создать отдельный Context для текущего legacy planning state с source project и copy/reference конфигурации, сохраняя history. Context ID новый, legacy Team ID не переименовывается.
4. **Неоднозначность.** Дубликаты A claims, conflicting A/B history либо неизвестная принадлежность ручных settings → LEGACY_BINDING_REQUIRED. Authorized owner видит минимальный diff и явно распределяет данные/оставляет архивный legacy Context. Нельзя автоматически размножить Alice, exclusions и published commitments во все новые Teams.
5. **Person reuse.** Сопоставить Resource references по проверенной external account identity внутри installation; старые resource IDs оставить aliases/profile identities. Не объединять по displayName. Membership и Team profile records остаются Team-specific; historical assignments не переписываются новым Team owner.
6. **Work и планы.** Создать SourceWorkIdentity/Context projection bindings, preserve manual override provenance, version/input/snapshot lineage. Legacy Project pointer переносится только в Context, которому принадлежит referenced roadmap; остальные Context не получают его копию. Неоднозначный pointer блокирует cutover, не «назначается последнему».
7. **Проверка/активация.** Compare before/after counts, IDs, effective memberships, exclusion precedence, calendars, mapping transforms, work scope, canonical values и current/history plans. Новый read path становится authoritative только после completed migration manifest. Retry после каждого write даёт тот же результат; old writer не может перезаписать migrated owner.

Switch A→B→A затем должен возвращать собственные people/work/planning state. Если provenance была утрачена раньше, честный результат — reviewed binding и сохранённый archive, а не обещание восстановить неизвестное автоматически.

## Расхождения с инструкциями и предыдущими документами

- [AGENTS.override](../../AGENTS.override.md) запрещает raw GraphQL/customer logging. Team GraphQL path использует safe allowlist, но generic `caught.message`/raw diagnostic body/stack handling остаются шире этого правила. Требуется изменение error contract и старых tests, сохраняющих exact details; факт реального раскрытия данных в logs в этом аудите не устанавливался.
- [Старая telemetry specification](../telemetry-and-diagnostics.md) допускает customer diagnostic details, включая raw evidence. Новый target минимизирует данные и разделяет audit/diagnostics; прежнее описание не оправдывает нарушение новой инструкции.
- [Старый persistence design](../persistence-model.md) описывает hourly migration trigger, тогда как [manifest](../../manifest.yml) содержит `fiveMinute` с временным diagnostic intent. Design SQL и executable migrations расходятся по `idx_teams_project_external`: не считать design index гарантированно установленным.
- Старые [domain](../domain-model.md)/[application architecture](../application-architecture.md)/[field mapping](../field-mapping.md) содержат project/team owners; current first multi-Team patch исправляет только часть paths. Новое target требование first-class Context имеет приоритет над сохранением старых owners.
- Будущие productivity идеи в старых материалах не входят в target: effort invariant PERSON_DAYS. CP-SAT v3 уже отвергает productivity input, его не надо возвращать ради совместимости текста.
- «Next milestone: do not implement until explicitly requested» из override не запрещает этот **явно запрошенный design**. Он не разрешает выполнять реализацию/deploy; здесь созданы только docs.
